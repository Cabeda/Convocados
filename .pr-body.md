## Summary

The connector's failure was never the sign-in screen. It dies **before consent**, and the authorization server is the reason.

Production evidence, read-only:

| What | Value |
|---|---|
| `oauthClient` rows named "Claude" | 3 — 13:42, 15:15, **16:49 (your re-add)** |
| `oauthConsent` rows | **0** |
| `oauthAccessToken` rows for a Claude client | **0** |

So registration works, then nothing. Replaying the exact request Claude sends — including the RFC 8707 parameter every MCP client adds — shows why:

```
GET /api/auth/oauth2/authorize?response_type=code&client_id=OdgHp…&redirect_uri=https://claude.ai/api/mcp/auth_callback
    &scope=openid profile email read:events create:events&code_challenge=…&code_challenge_method=S256
    &resource=https://convocados.cabeda.dev/api/mcp
→ 302 https://claude.ai/api/mcp/auth_callback?error=invalid_target
    &error_description=requested resource https://convocados.cabeda.dev/api/mcp is not configured
```

`@better-auth/oauth-provider` only accepts a `resource` that has an `oauthResource` row, and only for clients linked to it. We registered neither, so Claude's authorize request was refused outright — the user never reached a consent screen, and claude.ai reported a plain authentication failure. My earlier hand-test omitted `resource`, which is why it passed locally.

Fixing that exposed a second break: with an audience, the provider stops writing opaque `oauthAccessToken` rows and mints `at+jwt` tokens instead. `authenticateRequest` only looked up rows, so every MCP call with the new token returned 401. Making the tokens opaque again is not available — `disableJwtPlugin` is incompatible with `storeClientSecret: "hashed"` (id tokens would need the plaintext secret, and better-auth refuses at startup).

Four changes, all server-side (matching what you said: scopes and challenges come from the server, never from the user picking permissions):

1. **`resources` + `clientRegistrationDefaultResources` = `<base>/api/mcp`** in `oauthProvider`, so the resource Claude names is known and every newly registered client is linked to it.
2. **`src/lib/oauthResourceToken.server.ts`** — verifies a resource-scoped JWT against the `jwks` table: EdDSA signature (node:crypto, no new dependency), `iss` = `<base>/api/auth`, `aud` includes `<base>/api/mcp`, `exp` in the future. `authenticateRequest` falls back to it, so both opaque (mobile, trusted client) and JWT (MCP) tokens work.
3. **The 401 advertises the connector's whole scope set**, not the one tool being called. It was `scope="read:events"`; Claude builds its authorization request from that header, so consent minted a read-only token and every write failed.
4. **A missing scope now returns `403` with `WWW-Authenticate: Bearer error="insufficient_scope", scope="<everything still needed>"`** instead of a bare 403. Claude's authentication doc: a 403 without that challenge is a **terminal error** — no re-authorization, no retry. This is the "creating a game" symptom.

Requirements from Claude's checklist that were already met and are unchanged: 401 + `resource_metadata`, PRM `resource`, RFC 8414 metadata, S256 PKCE, DCR, `https://claude.ai/api/mcp/auth_callback`, form-urlencoded token endpoint, well under 10 s.
